五、机制解释
B vs A（同核竞争）

减速比 1.92，CPU% 从 109% 降到 54%，非自愿切换从 23 暴增到约 1243（约 54 倍）。

两个任务被 taskset 绑定到同一核心（CPU 0），CFS 调度器在时间片到期时反复切换，墙钟翻倍的主因是直接 CPU 核心竞争。

C vs B（异核对照）

减速比从 1.92 降到 0.81，非自愿切换从 1243 回落到 20—28（与基线同量级）。

异核把两个任务分别绑定到 CPU 0 和 CPU 4（属于不同 socket），彻底消除了 CPU 时间竞争。

D vs B（nice 对照）

nice=10 的任务减速比 1.89，几乎和 B 组一样慢；nice=0 的任务减速比 1.07，接近基线。

CFS 理论权重比约 9.3:1（nice 0 权重 1024，nice 10 权重 110），但实测比例只有约 1.76:1（29.37/16.72）。

六、替代解释
C 组比基线还快约 20% 的可能原因

基线三次波动较大（13.82—17.47s），均值被拉高。

异核运行时两个任务并行，缓存和内存访问被分散。

基线时可能有后台任务干扰，C 组恰好避开了。

这一点说明基线本身带有波动，绝对值比较需谨慎。

nice 实测权重比远低于理论值的可能原因

Python 解释器内部辅助线程也参与竞争。

虚拟机 CPU 调度层叠加了额外开销。

任务 A 只跑到 98% 而非 100%，核心未被两个任务同时占满。

运行时间不够长，平均效应未完全体现。

nice 表达的是调度权重"倾向"，不是精确时间配比。

当前仓库提交 8c9cc1b

当前 CentOS 7 / Python 3.6.8 环境

八、一分钟汇报草稿
我们使用固定工作量 CPU 任务（WORK=2598），基线平均 15.57 秒，CPU% 约 109%，非自愿切换约 23 次。

同核竞争时任务 A/B 平均 29.82/29.99 秒，减速比约 1.92/1.93；CPU% 降到约 54%，非自愿切换暴增到约 1243 次。这些证据支持直接 CPU 核心竞争是同核变慢主因的解释。

异核对照把两个任务分别绑到 CPU 0 和 CPU 4，减速比回落到约 0.81，非自愿切换回到 20—28 次。说明把任务放到不同核心可以基本消除 CPU 时间竞争。

nice 对照中，nice=10 的任务减速比 1.89，nice=0 的任务只有 1.07，说明 nice 在真实 CPU 竞争下有效，但实测权重比（约 1.76:1）远低于理论值（约 9.3:1）。

当前结论边界：适用于本次代码提交、当前 WORK=2598 配置、CentOS 7 虚拟机环境和 8 逻辑 CPU（无超线程）的拓扑。未验证在不同 WORK 值、不同 nice 值或宿主机负载变化下的表现。
